1. Executive Summary

ForenSight AI is a digital forensics investigation copilot designed to reduce the manual burden on investigators by automatically transforming raw forensic evidence into structured, queryable, and explainable investigation knowledge. Existing tools such as Autopsy, FTK and EnCase are excellent at collecting and presenting evidence, but they leave the analyst to manually inspect thousands or millions of events and infer cause-effect relationships. ForenSight AI ingests heterogeneous forensic data — disk images, memory dumps, network captures, and mobile or cloud extractions — normalizes the events into a common fact model, links them into a per-case knowledge graph, and assists the investigator with an LLM-driven reasoning layer that can answer natural-language questions, summarize timelines, and suggest next investigative steps.

This document describes the technical architecture at a depth appropriate for a two-person team with a three-week timeline, runnable on a developer laptop, using open-source components throughout. The full architecture covers all four data sources; the three-week deliverable is a hard-scoped slice of it (see Section 12) that demonstrates every layer end-to-end on a single representative source plus one auxiliary source.

2. Problem Statement

A modern forensic investigation produces overwhelming volumes of evidence. A 500 GB disk image typically yields several million filesystem events, tens of thousands of registry entries, browser histories, deleted artefacts, and user-attributable actions. A single hour of network capture can contain millions of packets. Memory dumps and mobile extractions add yet more structured noise. The investigator's job is not to look at all of this — it is to find the small subset of events that constitute the story of what happened.

Today, that subset is found mostly by hand. Investigators write SQL queries against case databases, click through file trees in Autopsy, and rebuild timelines in spreadsheets. Cross-case knowledge — the fact that a similar registry persistence technique was used in a case three months ago — lives in the analyst's head.

2.1 Gaps in current tools

  • Tools surface evidence but do not infer relationships between events across data sources.
  • There is no shared semantic model — disk events, network events, and mobile events live in incompatible schemas.
  • Investigators cannot ask the case natural-language questions; they must translate every question into a query.
  • Knowledge from prior investigations is not retrievable; each new case starts from scratch.
  • Reports are written from notes; the link back to underlying evidence is informal.

3. Objectives

  1. Acquire and ingest forensic evidence from disk images, memory dumps, network captures, and mobile or cloud extractions while preserving cryptographic integrity.
  2. Normalize all extracted artefacts into a common fact model so events from different sources can be reasoned about together.
  3. Build a per-case knowledge graph that captures entities (files, processes, users, hosts, IPs, accounts) and the relationships between them.
  4. Correlate events across sources using time, identity, and causal heuristics to produce candidate event chains.
  5. Compare the current case against an embedding index of past cases to surface similar techniques, indicators, and modus operandi.
  6. Provide an AI copilot, grounded in the case knowledge graph through retrieval-augmented generation, that answers investigator questions in natural language with citations back to the underlying evidence.
  7. Produce defensible, evidence-linked output that an investigator can include in a forensic report.

4. System Overview

ForenSight AI is built as a six-layer pipeline. Each layer has a single responsibility and communicates with the next through well-defined data contracts. This separation makes it possible to swap individual parsers, storage backends, or LLM providers without touching the rest of the system.

4.1 Conceptual data flow

  RAW EVIDENCE          -> Disk image (E01/dd), RAM dump, PCAP, mobile
         |                 extraction (UFDR/AFU), cloud export (JSON)
         v
  ACQUISITION LAYER     -> Hash, mount read-only, verify integrity
         |
         v
  PARSING LAYER         -> Autopsy/dfvfs, Volatility3, Zeek/tshark,
         |                 ALEAPP/iLEAPP, custom cloud parsers
         v
  NORMALIZATION LAYER   -> Common Fact Model (entity, event, relation)
         |
         v
  STORAGE LAYER         -> Case DB (Postgres) + Graph (Neo4j) +
         |                 Object store (filesystem) + Vector DB
         v
  REASONING LAYER       -> Correlation rules, graph queries, ML models,
         |                 cross-case similarity
         v
  AI COPILOT LAYER      -> RAG over graph + docs, natural-language Q&A,
         |                 summarisation, next-step suggestions
         v
  PRESENTATION LAYER    -> Web UI, timeline, graph view, report export

The acquisition and parsing layers are dominated by existing open-source tooling — ForenSight AI is not a new disk parser. Our contribution lives in the normalization, storage, reasoning, and copilot layers, where we transform tool output into investigation knowledge.

5. Architectural Layers

5.1 Acquisition Layer

The acquisition layer is responsible for taking custody of raw evidence and proving, mathematically, that it has not been modified after intake. Every artefact entering the system is hashed (SHA-256 and SHA-1 for cross-tool compatibility), the hash is recorded in the case database alongside the artefact metadata, and the original file is mounted read-only or copied into an immutable evidence store.

Responsibilities

  • Compute and persist cryptographic hashes for every incoming file.
  • Maintain a chain-of-custody log: who uploaded what, when, from where.
  • Detect evidence type by magic bytes and file extension and route to the correct parser.
  • Reject or quarantine evidence whose hash does not match a recorded reference value.

5.2 Parsing Layer

Parsing converts source-specific binary or proprietary formats into structured Python objects. We do not write parsers from scratch; we wrap mature open-source libraries and tools and capture their output through a normalized adapter interface.

SourcePrimary tool / libraryArtefacts extracted
Disk images (E01, dd, raw) dfVFS, pytsk3, Autopsy CLI Filesystem timeline, MFT, registry hives, browser history, recycle bin, prefetch, shellbags
Memory dumps Volatility 3 Process tree, network sockets, loaded DLLs, injected code, command history
Network captures (PCAP) Zeek, tshark, Scapy Flows, DNS queries, HTTP/TLS metadata, file carving, IDS alerts
Mobile (Android / iOS) ALEAPP, iLEAPP, MVT App data, messages, call logs, location, installed packages, notifications
Cloud exports Custom JSON adapters (Google Takeout, Microsoft eDiscovery) Login events, file access logs, OAuth grants, sharing activity

5.3 Normalization Layer — the Common Fact Model

This is the architectural heart of ForenSight AI. Every parser, regardless of source, emits records that conform to a single schema we call the Common Fact Model. A normalized record always contains an entity (the thing the fact is about), an event (the action or observation), a timestamp interval, a source reference (which artefact and offset), and an integrity reference (hash of the originating evidence).

Schema (simplified)

Entity {
  id: UUID,
  type: enum(FILE, PROCESS, USER, HOST, IP, DOMAIN, ACCOUNT, DEVICE,
             REGISTRY_KEY, MESSAGE, APP),
  canonical_name: string,
  attributes: jsonb        # e.g. {path, size, hash, owner_sid}
}

Event {
  id: UUID,
  type: enum(CREATE, MODIFY, ACCESS, DELETE, EXEC, CONNECT, AUTH,
             SEND, RECEIVE, INSTALL, LOGIN, LOGOUT, PERSIST),
  timestamp_start: timestamptz,
  timestamp_end: timestamptz NULL,
  primary_entity_id: UUID,
  secondary_entity_id: UUID NULL,
  source_artefact_id: UUID,
  evidence_offset: bigint NULL,
  confidence: float        # 0.0 - 1.0
}

Relation {
  src: UUID, dst: UUID,
  type: enum(PARENT_OF, OWNS, CONTACTED, EXECUTED, ACCESSED,
             RESOLVES_TO, AUTHENTICATED_AS, LOCATED_AT),
  weight: float,
  derived_from: [EventID]  # provenance
}

Provenance is non-negotiable. Every fact in the system traces back to a parser run on a hashed artefact at a known offset. Without this, the AI copilot's answers would not be defensible in a forensic context.

5.4 Storage Layer

Different parts of the system want different views of the same data. We use four cooperating stores rather than forcing one engine to do everything badly.

StoreEngineHoldsWhy
Case relational DB PostgreSQL 16 Cases, users, artefacts, raw normalized facts, audit log Strong transactions, JSONB, mature
Knowledge graph Neo4j Community Entities and relations, Cypher queries for traversal Native graph traversals, visual browser
Object / evidence store Local filesystem, WORM-style write-once layout Original disk images, memory dumps, PCAPs Simple, no cloud cost, easy hashing
Vector index Qdrant (or Chroma) Embeddings of artefact summaries and prior-case notes Powers similarity search and RAG

5.5 Reasoning & Correlation Layer

Once events are in the knowledge graph, the reasoning layer derives higher-order facts. It is the layer that turns "a process was executed" and "a network connection was made" into "this process initiated this connection". Three complementary techniques are used:

5.5.1 Rule-based correlation

A library of hand-written rules expressed in Cypher and Python operates over the graph. Each rule reads a pattern, asserts a derived relation, and records its provenance. Example rules include temporal-proximity binding of a process execution to an outbound socket, matching a downloaded file's hash to the file it was later persisted as, and detecting registry Run-key persistence.

5.5.2 Statistical and ML-based correlation

Where rules are too brittle, we use lightweight ML. A clustering pass over filesystem events groups bursts of activity into user sessions. A small classifier (gradient-boosted trees via scikit-learn or LightGBM) flags processes whose behaviour profile matches known malware families. None of this requires GPU training; pre-trained models ship with the system and only get fine-tuned on case-specific data when needed.

5.5.3 Cross-case similarity

Every case produces a set of artefact summaries — short structured descriptions of techniques and indicators observed. These are embedded with a sentence-transformer model and indexed in Qdrant. When a new case is loaded, the reasoning layer queries the index to surface the top-K most similar prior cases and lists overlapping techniques. This is how "compare with previous investigations" is implemented.

5.6 AI Copilot Layer

The AI copilot is a retrieval-augmented chat interface that sits on top of the knowledge graph. It is not a general-purpose chatbot; it is a constrained reasoning agent with access to a small set of tools and a strict requirement to cite evidence.

5.6.1 Architecture

User question
    |
    v
  Intent classifier (small local model)
    |--- factual lookup  --> graph query tool (Cypher)
    |--- timeline        --> timeline query tool
    |--- similarity      --> vector search tool
    |--- summarisation   --> document retriever
    v
  Retrieved context (facts + provenance)
    |
    v
  LLM (Llama 3 8B via Ollama, or Gemini / Claude API)
    |  - system prompt enforces citation format
    |  - response must reference Event IDs
    v
  Rendered answer with hyperlinks to underlying artefacts

5.6.2 Guardrails

  • The LLM never sees raw evidence. It only sees normalized facts that are already in the graph, so it cannot hallucinate file paths that do not exist.
  • Every claim in a generated answer must be backed by at least one Event ID. The UI greys out unsupported sentences.
  • All copilot interactions are logged with the prompt, retrieved context, and final response, forming an auditable trail.

5.7 Presentation Layer

The frontend is a single-page web application that presents three core views: a case dashboard with timeline and key indicators, an interactive graph explorer for walking entities and relations, and a chat panel for the copilot. Report export produces a Word or PDF file with embedded evidence references.

  • Framework: React 18 with TypeScript.
  • Visualisation: Cytoscape.js for graph, vis-timeline for events, Recharts for distributions.
  • Auth: simple JWT against the case database; not multi-tenant in this scope.

7. Knowledge Graph Design

The knowledge graph is the durable record of what we know about a case. Its schema is intentionally small — six node types and ten relation types — so that anyone can read a Cypher query and understand it immediately.

Node labels

  • File — any filesystem object, including deleted and carved files.
  • Process — any executing or previously-executed program instance.
  • User — local or domain account observed in any source.
  • Host — physical or virtual machine; one per case is typical at this scale.
  • NetworkEndpoint — IP, domain, or URL contacted.
  • Artefact — the originating evidence container (disk image, memory dump, PCAP, mobile extraction).

Relation types

  • EXECUTED — Process executed File.
  • PARENT_OF — Process parent of Process.
  • ACCESSED, MODIFIED, DELETED — User or Process to File.
  • CONNECTED_TO — Process to NetworkEndpoint.
  • RESOLVES_TO — NetworkEndpoint (domain) to NetworkEndpoint (IP).
  • AUTHENTICATED_AS — Host to User.
  • EXTRACTED_FROM — every node has at least one such edge to an Artefact, preserving provenance.
  • DERIVED_BY — links a relation to the correlation rule or model that produced it.

Example Cypher — "what did process X touch?"

MATCH (p:Process {pid:1234})-[r:ACCESSED|MODIFIED|DELETED|CONNECTED_TO]->(t)
WHERE p.case_id = $caseId
RETURN p, r, t
ORDER BY r.timestamp_start

8. AI Copilot — Prompt and Retrieval Design

The copilot's behaviour is governed almost entirely by its system prompt and the contract it has with the retrieval tools. The LLM itself is interchangeable.

System prompt (abbreviated)

You are ForenSight, a digital forensics assistant.
You answer questions about the active investigation case only.
Every claim you make must cite at least one Event ID from the
supplied context, written as [E:<uuid>] inline. If the context
does not contain enough information to answer, say so explicitly.
Do not speculate about evidence that is not in the context.
Format timestamps in UTC, ISO-8601.
When suggesting next steps, suggest concrete graph queries or
additional parsers to run, not vague recommendations.

Retrieval flow

  1. Classify the user's intent into one of: factual, timeline, similarity, summarisation, recommendation.
  2. Issue the corresponding tool call — Cypher query, timeline range query, vector search, or document retrieval.
  3. Rank the returned facts by confidence, recency, and graph-degree.
  4. Truncate the context to fit the model's window (8K for local Llama, 32K+ for API models), preserving Event IDs.
  5. Generate the answer; post-process to verify every sentence has at least one citation; flag the ones that do not.

9. Integrity, Security, and Chain of Custody

A forensic system is only credible if it can prove that nothing inside it has been tampered with. The architecture enforces this with three mechanisms:

  • Hash-on-ingest: every uploaded artefact is hashed before it is written to the evidence store; the hash is the artefact's primary key.
  • Append-only audit log: every API call that mutates state writes a row to an append-only table that includes the actor, timestamp, action, and a hash of the previous row (Merkle-style chain).
  • Read-only mounts and copy-on-read: parsers never write back to the original evidence; they operate on snapshots and the snapshots themselves are hashed.

10. Module Breakdown by Data Source

10.1 Disk Images and Filesystems

  • Mount the image read-only via dfVFS.
  • Walk the filesystem; for each file emit a FILE entity with hash, path, MAC times, owner.
  • Parse NTFS MFT directly to recover deleted entries and timestamps that the filesystem walk misses.
  • Parse registry hives (SYSTEM, SOFTWARE, NTUSER.DAT) for autostart, USB plug history, ShellBags using python-registry.
  • Parse browser histories (Chrome, Firefox, Edge) into MESSAGE / ACCESSED events.

10.2 Memory Dumps

  • Run Volatility 3 plugins: pslist, pstree, netscan, malfind, cmdline, dlllist.
  • Each row emitted by a plugin becomes a normalized Process or NetworkEndpoint entity with a CONNECTED_TO or EXECUTED edge.
  • Confidence is set lower for memory-only facts because RAM forensics is inherently more probabilistic than disk.

10.3 Network Captures

  • Convert the PCAP with Zeek to obtain conn.log, dns.log, http.log, ssl.log, files.log.
  • Each conn.log row becomes a CONNECTED_TO relation between local Process (joined via memory data) and a NetworkEndpoint.
  • DNS resolutions become RESOLVES_TO edges. This is what enables "this process talked to this domain" queries.

10.4 Mobile and Cloud

  • ALEAPP / iLEAPP produce HTML and JSON reports; we parse the JSON only.
  • Messages, call logs, and location pings become MESSAGE-typed Event records, each tied to an APP entity and a USER entity.
  • Cloud exports (Google Takeout, Microsoft eDiscovery) are parsed by per-provider adapters; their schemas are stable and well-documented.

11. Deployment Architecture

All components run as Docker containers orchestrated by a single docker-compose.yml. The system is brought up with one command and torn down the same way. No Kubernetes, no cloud provider, no managed service — appropriate for an offline, evidence-handling workload.

services:
  postgres:  image: postgres:16
  neo4j:     image: neo4j:5-community
  qdrant:    image: qdrant/qdrant
  redis:     image: redis:7
  api:       build: ./backend  (FastAPI + Celery worker)
  worker:    build: ./backend  (Celery worker, parser-heavy)
  ollama:    image: ollama/ollama  (optional, for local LLM)
  web:       build: ./frontend (React, served by nginx)

Total memory footprint at idle is approximately 4 GB; with a 1 GB disk image being parsed it peaks around 8 GB. The whole stack runs on a developer laptop.

12. Project Scope (Two People, Three Weeks)

The architecture above is the full vision. With a two-person team and a three-week window the deliverable is a hard-scoped vertical slice: every layer is present, but only enough of each to demonstrate the pipeline end-to-end on a real dataset. Anything not on the "in scope" list is explicitly deferred.

In scope

  • Two data sources only — one disk image and one matching memory dump from a single public CTF dataset (e.g. NIST Hacking Case or a Digital Corpora scenario). PCAP and mobile parsing are demonstrated as stub adapters only.
  • Common Fact Model with four entity types (File, Process, User, NetworkEndpoint) and six relation types (EXECUTED, ACCESSED, MODIFIED, CONNECTED_TO, PARENT_OF, EXTRACTED_FROM).
  • Three rule-based correlations: process-to-network binding by time, registry Run-key persistence, parent-child process chain.
  • AI copilot with two question intents only — factual lookup and timeline summarisation — using a hosted API LLM (Gemini Flash or Claude Haiku) for speed. No local LLM in this slice.
  • Minimal web UI: case dashboard, graph view (Cytoscape.js), and chat panel. No standalone timeline component in v1.
  • Hash-on-ingest, append-only audit log.
  • Report export skipped in v1; copy/paste from chat is acceptable for the demo.

Explicitly deferred

  • Full PCAP, mobile, and cloud parsers (stubs only).
  • ML-based correlation and cross-case similarity.
  • Local LLM via Ollama.
  • Multi-tenant access control.
  • Carving, mobile decryption, cloud connector auth, multi-node deployment.
  • Word/PDF report export.

14. Evaluation Plan

Because forensic correctness is the whole point, evaluation is taken as seriously as implementation.

  • Ground-truth comparison on a public CTF case where the correct answer to investigative questions is known. Metrics: precision and recall of recovered events; precision and recall of generated answers' citations.
  • Time-to-first-insight: how long, from ingest to first useful correlation, the system takes versus an unaided analyst using Autopsy. Target: 5× faster.
  • Copilot answer quality: blind rating by three peers on a 5-point scale across faithfulness, completeness, and usefulness.
  • Integrity audit: random sampling of stored artefacts to re-verify their hashes match the ingest record. Target: 100% match.

18. Glossary

  • Artefact — a piece of original evidence (e.g. a disk image file), as opposed to a fact derived from it.
  • Common Fact Model — the normalized schema (Entity, Event, Relation) used across all data sources.
  • Provenance — the chain of references that lets any fact in the graph be traced back to a hashed artefact at a known offset.
  • RAG (Retrieval-Augmented Generation) — pattern of supplying an LLM with retrieved factual context before generation, so its answers are grounded.
  • Cypher — Neo4j's query language; the pattern-matching equivalent of SQL for graphs.
