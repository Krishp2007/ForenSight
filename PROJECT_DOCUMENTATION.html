🛡️ ForenSight AI Technical Documentation

Developer-level Architecture, Data Flow, Technology Deployment Locations, API Specs, and AI Engineering Guide.

1. Project Overview

ForenSight AI is an enterprise AI-driven Digital Forensics & Incident Response (DFIR) platform designed to automate log parsing, anomaly detection, process execution graph correlation, and natural language AI copilot investigations.

Core Technologies

  • Frontend: React 18, Vite, React Router v6, Axios, Lucide Icons, Vis-Network.
  • Backend Framework: FastAPI 0.110.0+ with Uvicorn ASGI server.
  • Databases: MongoDB (Motor async BSON), Neo4j (Graph DB), MinIO (S3 Storage), FAISS / Qdrant.
  • AI & ML Stack: Google Gemini 2.0 Flash REST API, PyOD Isolation Forest, SentenceTransformers (all-MiniLM-L6-v2).

4. Folder Explanations

backend/app/api/

Purpose: Defines HTTP REST endpoints for the FastAPI application.
Contains: Routers (auth.py, cases.py, evidence.py, events.py, chat.py, graph.py).
Used by: React Frontend Axios API client.
Data handled: JSON request payloads, file uploads, JWT auth headers, HTTP responses.

backend/app/parsers/

Purpose: Forensic log parsing engine converting raw evidence files into normalized event schemas.
Contains: evtx_parser.py, pcap_parser.py, browser_parser.py, csv_parser.py, text_parser.py.
Used by: ProcessingPipeline background ingestion service.

backend/app/repositories/

Purpose: Data Access Object (DAO) layer encapsulating database queries.
Contains: case_repository.py, evidence_repository.py, event_repository.py, graph_repository.py, user_repository.py.

5. File-by-File Documentation

backend/app/services/ingestion/processing_pipeline.py

Master asynchronous evidence processing pipeline. Downloads raw evidence from MinIO, dispatches to parsers, bulk inserts into MongoDB, syncs Neo4j graphs, trains PyOD Isolation Forest, and builds FAISS vector indices.

backend/app/services/copilot/gemini_provider.py

Communicates with Google Gemini API via REST endpoints. Automatically rotates across gemini-2.0-flash, gemini-1.5-flash, and gemini-1.5-pro on rate limits.

backend/app/services/copilot/report_generator.py

Formats investigation findings into paragraph-wise Markdown reports matching ChatGPT/Gemini style.

38. ForenSight AI RAG Architecture & Zero-Hallucination Grounding

ForenSight AI implements a case-isolated Retrieval-Augmented Generation (RAG) architecture powered by Google Gemini 2.0 Flash REST API and local FAISS vector search.

  • Frontend Chatbox: ChatPanel.jsx & ChatMessage.jsx (React 18) with history context window support.
  • Backend Chat API: POST /api/v1/cases/{case_id}/copilot in backend/app/api/chat.py
  • Deterministic Query Router: query_router.py routes greetings, evidence lists, file security assessments, and counts to direct database queries with entity resolution.
  • Zero-Hallucination Policy: Completely purged static demo strings. Inquiries regarding unknown threats or files with zero anomaly detections return Confidence: Insufficient Evidence.
  • Fenced Prompt Engine: prompts.py encloses evidence in <FORENSIC_EVIDENCE> XML tags for prompt-injection defense.
  • Case Isolation: FAISS vector indexes are strictly stored per-case at /vector_indexes/{case_id}/ ensuring zero cross-case data leakage.
  • Source Citations & Confidence: Returns structured JSON with grounded answers, confidence ratings (High/Medium/Low/Insufficient Evidence), and explicit source citations.

39. Evidence Data Lifecycle & Cascade Deletion

Deleting an evidence file triggers a guaranteed synchronous 100% cascade cleanup across all storage tiers:

  • MongoDB Evidence: Deletes primary record from evidence collection.
  • MongoDB Events: Deletes parsed log events matching evidence_id as BSON ObjectId or String.
  • Neo4j Graph: Deletes FORENSIC_ACTION edges, purges orphan entity nodes, and executes DETACH DELETE on all case nodes if 0 files remain.
  • FAISS Vector Store: Rebuilds vector index for case, or removes index.faiss and metadata.pkl disk files if 0 events remain.
  • MinIO Storage: Deletes raw binary object from MinIO S3 bucket.
  • Audit Logs: Deletes evidence audit entries from both audit_log and audit_logs collections.

40. Evidence Status & Scan Time Lifecycle Synchronization

The backend database (MongoDB) is the single authoritative source of truth for evidence status and scan timestamps.

  • Status Transitions: uploaded → queued → parsing → parsed (or failed).
  • Server Timestamps: created_at (upload time), parsing_started_at (parse start time), parsed_at (parse completion time).
  • Live Scan Duration: Displays live ticking seconds (0s, 1s, 2s...) starting from created_at while in-flight, freezing to exact server duration upon completion.
  • Real-Time Synchronization: 2-second interval polling (POLLING_INTERVAL = 2000) for active items automatically synchronizes status and timestamps.
